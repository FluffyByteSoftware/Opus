The three programs

Opus is three programs. One the player opens, one the player plays, and one that runs the whole show on my machine.

The one idea everything hangs off: the server is the boss. The client asks, the server decides. The client never gets sent anything it isn't allowed to see, because somebody with a hacked client can read anything it's sent.

Step 1: the patcher checks your files

You double-click Soundcheck. Before it lets you type a password, it checks that every file of the game on your disk is the one we shipped. Not "most of them": every one. Here's the trick that makes it cheap.

A fingerprint here is a SHA-256: you feed a file through a maths grinder and get 64 characters out, and changing one byte of the file changes the whole fingerprint. So "same fingerprint" means "same file", and the launcher never has to send your files anywhere to prove it.

The admin side is the same program with --admin. I point it at a build, press PUBLISH, and it copies the build into the web folder and writes the manifest beside it. A plain web server serves that folder as it is. Conductor isn't involved in patching at all.

Why bother? Two reasons. A player with a broken install gets fixed without reinstalling 600 MB. And a player with a modified install gets it put back, which is step one of keeping cheats out.

Step 2: the login (the bouncer)

Files pass, the boxes unlock, you type your username and password and hit SUBMIT. Soundcheck opens one connection to the server on TCP, wrapped in TLS, which is the same encryption your bank uses. Then it's a short conversation.

Why the password turns into a key first

The launcher never sends your actual password. It grinds it (with your username mixed in) into a 64-character key, and sends that. The server grinds it again with a slow, memory-hungry recipe called Argon2 before comparing. If somebody ever stole the database they'd have the result of two grinders, not a single password anybody can reuse on their email. "Remember me" saves the key, not the password, for the same reason.

Why "Invalid Credentials" is the only wrong answer

Wrong username, wrong password, wrong secret word: you get the same words, and the server always takes at least 150 ms to say it. So nobody can tell which part they got wrong, or whether an account exists, by watching the answer or the clock.

PLAY is a second login

SUBMIT's ticket is thrown away. When you press PLAY, Soundcheck logs in again with the key still in memory, gets a fresh ticket, hands it to Ensemble, and closes. So no half-used ticket ever sits around, and the server lets the first one die.

Step 3: the game (UDP, the fast lane)

Soundcheck starts Ensemble and puts four things in its environment (not on its command line, where other users on the machine could read them): the server's address, the UDP port, the token, and where Soundcheck itself lives (for the trip back). Ensemble never sees a password and never speaks TCP. It goes straight to the UDP port.

TCP vs UDP, in one breath. TCP is a phone call: every word gets there, in order, or the line drops. UDP is shouting across a field: fast, no setup, but a word can get lost. The login needs the phone call. A game needs the field, and it just shouts again if nobody answers.

Little things that matter

  • The anti-flood. After a command you wait 500 ms (two ticks) before the next one is listened to; /who makes you wait a second because it costs more. Spam just gets "too soon".
  • Big answers come in pieces (Spans). A /who list with thirty people won't fit one packet, so it's cut into "piece 2 of 5" and glued back together on the client.
  • No way back to character select. Leaving the world for any reason (kicked, server stops, /camp, LOG OUT) means the launcher again. Simple on purpose.
  • A character is locked for a second when it's loading and for a second after it leaves, and until its save has landed. Pick a locked one and you're told to wait, then pulled in.

The way back

When the session ends, Ensemble starts Soundcheck again (it knows where, from its environment), hands it why ("You were kicked by the admin.", "Logged out."), and quits. So you're looking at the login with the reason in the status box, not a dead black window. /camp desktop and QUIT skip the launcher and just close.

The test client (a fake player in a script)

Conductor/dev/networking/test_client.py is a Python script that pretends to be a client, using nothing but Python's standard library. It does the whole dance above from a terminal: TLS, Hello, Login with the key, the Ticket, Connect over UDP, the character list, PLAY, and then whatever you type goes out as a /chat. Two of them in two terminals can talk to each other.

It exists because for a long time there was no Ensemble to test with, and it's still the quickest way to poke the server: no Unity, no launcher, one line. When the protocol document changes, the script changes with it, same as the real clients. If the script and the server disagree about a byte, the document says who's right and the code gets fixed.

The three readers of one page. Conductor's protocol.rs, Ensemble's Protocol.cs, and test_client.py are all written from PROTOCOL.md. That's why they agree.

The library: what a "thing in the world" is made of

Inside Conductor, the game library is primlib. It's how the server holds every goblin, player and rock in memory. The style is called an ECS, which sounds fancy and isn't.

Entities, components, and a spreadsheet

Picture a spreadsheet. Each row is a thing (an entity). Each column is a kind of fact about a thing (a component): where it is, what it looks like, its health. A thing has a value in some columns and nothing in others. A rock has a position and a shape and no health. A player has all of it.

The eleven kinds of fact, in plain words: where it is (Transform), what it looks like (Model, PrimitiveShape, Animator), what it's called (ShortName, LongName, Titles), its bars (Health, Endurance, Mana), and whose it is (PlayerCharacter, which points at the account).

Templates and blueprints (the cookie cutter and the icing)

You don't fill the spreadsheet by hand. A template is a cookie cutter: "an NPC has these columns, with these defaults". A template can include another one whole: Character takes in everything Living has, then adds its own. A blueprint is the icing on one cutter: goblin_a is the NPC template with its own model, name and health. Every thing remembers which templates it came from, so the game can ask is(entity, "Living") and get a yes or no.

Saving

The World lives in memory and the game loop never waits on the database. Every 150 seconds one tick copies every player's character as plain data, and a background thread turns the copies into Lua text and writes them all in one go, so the database holds the world as it was at one moment. Each component says which of its fields get saved and which don't. STOP SERVER saves one last time. When you log in, your character is built from the Character template with your save laid over the top.

The tick (the server's heartbeat)

Conductor doesn't do things "when they happen". It does them on a beat: every 250 ms, five checks of 50 ms, in a fixed order, run by the GameClock. Only the GameClock's thread is allowed to touch the World and the ground. Everything slow (the database, the disk, the network) happens on other threads and hands its answer in later.

The ground is blocks, one metre a side, in chunks of 32, in a world 16 km across and eleven chunks tall (bedrock at the bottom, nothing above +319). It's made on its own thread, chunk by chunk, and the server's door only opens once the ground around 0,0,0 is in, because nobody should log in before there's a voxel to stand on. Getting that ground onto the client's screen is the next hard part.

What isn't there yet

  • The world on the client's screen. The server has the ground; Ensemble doesn't draw it yet. The plan is a rough "smoothed" map shipped with the client (through the patcher, as a file of its own) so the distance isn't empty, with the chunks around you streamed over UDP. This is the next big thing.
  • Movement. Nobody walks yet. The movement check in the tick is empty.
  • Windows. Conductor builds and runs there; Soundcheck and the new Ensemble haven't been tried there at all.
  • The launcher patching itself is written and untested, since the launcher doesn't ship beside the game yet.
  • A certificate for every client (so the server can turn away any connection that isn't a real install) is the long game, and the reason the launcher exists at all.
